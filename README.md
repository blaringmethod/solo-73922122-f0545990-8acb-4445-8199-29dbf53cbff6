# 货运数仓来源核对

货运数仓收到两份没标版本的导出 CSV(运单表导出、签收表导出),本工具用一份
JSON 证据包(两表起点快照 + 起止提交号 + 逐事务行变更前后值)重放提交历史,
判断两份 CSV 是否可能来自同一次提交。后续事务日志到达后,可在同一轮核查中
上传**续查包**继续核对更晚的提交,无需重传两张全表。

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000
```

页面上传三份文件:运单导出 CSV、签收导出 CSV、证据包 JSON。
页面底部可直接下载样例三件套试跑(预期交集:提交 100、102、106、108、110)。

初查证据有效后,结论下方会给出**本轮链接**(`/round/<id>`)。后续日志到达时,
打开该链接上传续查包即可接着核对;轮次页提供两个样例续查包
(110→116、116→118),依次上传可看到跨批相邻区间自动合并(110–111、116–118)。

本地自测(不需要 Docker):

```bash
pip install -r requirements.txt   # HTTP 接口测试需要 fastapi/httpx
python3 -m tests.selftest
```

## 输入格式

### 运单导出 CSV

只含已签收运单,列:`单号,状态,件数`(UTF-8,键 `单号` 不可重复)。

### 签收导出 CSV

只含已签收运单的签收明细,列:`签收号,单号,实收件数`(键 `签收号` 不可重复)。

### 证据包 JSON(初查)

```json
{
  "start_commit": 100,
  "end_commit": 110,
  "snapshots": {
    "waybills": [{"单号": "WB0001", "状态": "已签收", "件数": 3, "目的地": "上海"}],
    "receipts": [{"签收号": "RC0001", "单号": "WB0001", "实收件数": 3, "签收人": "张三"}]
  },
  "transactions": [
    {"commit": 101, "changes": [
      {"table": "waybills", "op": "update", "key": "WB0001",
       "before": {"单号": "WB0001", "状态": "已签收", "件数": 3, "目的地": "上海"},
       "after":  {"单号": "WB0001", "状态": "已签收", "件数": 4, "目的地": "上海"}}
    ]}
  ]
}
```

- 表名支持 `waybills`/`运单表`、`receipts`/`签收表`;`op` 为 `insert`/`update`/`delete`
  (insert 的 `before` 为 null,delete 的 `after` 为 null)。
- 快照行可含任意额外列,导出比对只取规定字段;但变更 `before` 必须与重放出的
  整行完全一致(含额外列),否则视为前值对不上。
- 数值比较按字符串归一化:JSON 数字 `3` 与 CSV 文本 `"3"` 视为相等。

### 续查包 JSON(续查)

```json
{
  "start_commit": 110,
  "end_commit": 116,
  "transactions": [
    {"commit": 111, "changes": [
      {"table": "receipts", "op": "update", "key": "RC0001",
       "before": {"签收号": "RC0001", "单号": "WB0001", "实收件数": 3, "签收人": "张三"},
       "after":  {"签收号": "RC0001", "单号": "WB0001", "实收件数": 4, "签收人": "张三"}}
    ]}
  ]
}
```

- `start_commit` 必须等于本轮**当前终点**,`end_commit` 必须更晚;
  事务明细格式与初查证据包相同,提交号从 `start_commit+1` 连续到 `end_commit`。
- **不复制两张全表**:续查包不携带 `snapshots`,只重放新事务
  (初查终点状态由服务进程保存)。

## 判定规则

- 导出视图:运单导出 = 状态为「已签收」的运单,取(单号, 状态, 件数);
  签收导出 = 单号属于已签收运单的签收行,取(签收号, 单号, 实收件数)。
- 只在**起点**(起始提交号)和**每笔事务整体应用之后**与 CSV 比对;
  键集合与对应值完全一致(按编号和值)记为一个吻合提交。
- 输出:各文件完全吻合的提交区间、两者的交集;交集为空时提示
  「所查范围内没有共同来源」。
- 下列情况提示「证据不足」并停止核查:
  - 日志缺号:提交号不连续、尾部缺失或超出终止提交号;
  - 变更前值与重放状态对不上(含 insert 前键已存在、update/delete 前键不存在);
  - 起点快照键重复或缺键列。
- 变更条数上限 50000 条/包,超出直接拒绝。

## 续查规则

- 初查证据有效后建立本轮核查,页面给出本轮链接;轮次保存在**同一服务进程**
  内存中,链接在进程内可重新打开(进程重启即失效)。
- 续查包从当前终点接到更晚的提交,逐条核对前值,按每笔事务完成后的状态
  计算两份 CSV 的吻合区间与交集;**跨批相邻区间自动合并**
  (如上批止于 110 且吻合、本批 111 也吻合,则合并为 110–111)。
- **整包通过才更新**:校验期间页面展示的仍是上次结果;缺号或前值不符时
  整批退回,原终点、两表状态与结果全部保留,改正后可从原终点重传。
- **并发互斥**:两个页面同时从同一终点提交有效续包时,只有一份生效
  (先持锁者),另一份收到 `stale_endpoint`(HTTP 409)提示终点已变,
  响应中附带当前最新状态。
- 进程内最多保留 128 个轮次,超出按最久未用淘汰(`app/rounds.py` 中
  `MAX_ROUNDS`)。

## 接口一览

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 初查操作页 |
| POST | `/api/verify` | 初查(multipart:两份 CSV + 证据包),证据有效时返回 `round_url` |
| GET | `/round/{id}` | 续查轮次页(当前状态 + 续查上传) |
| GET | `/api/round/{id}` | 轮次当前结果 JSON |
| POST | `/api/round/{id}/continue` | 续查(multipart:续查包 JSON) |
| GET | `/api/sample/*` | 样例 CSV / 证据包 / 续查包下载 |

续查响应 `status`:`ok` / `no_common_source` / `insufficient_evidence`(整批退回)
/ `stale_endpoint`(409,终点已变)/ `invalid_input`(400)/ `not_found`(404)。

## 性能设计

不为每次提交复制整表。重放时维护:

- 两张表的当前行(按主键的字典);
- 已签收单号集合、单号 → 签收号索引;
- 两个「当前导出视图 vs 目标 CSV」的差异计数器。

每条变更只触碰受影响的键:运单变更 O(1) 更新运单侧计数,签收状态翻转时只扫描
该单号名下的签收行;签收变更 O(1)。整体复杂度 O(快照行数 + 变更条数),
5 万条变更在本机自测约 2 秒内完成(见 `tests/selftest.py`)。

续查在引擎状态的**结构克隆**上进行(行对象不可变、容器浅拷贝),整包通过后
原子替换轮次状态,因此失败的批次不会污染原状态,校验期间读取到的仍是上次结果。

## 自测覆盖

`python3 -m tests.selftest`:

1. 样例场景端到端区间/交集断言;
2. 每个提交后增量计数与全量重算一致(验证不复制整表的增量逻辑正确);
3. 交集为空 → 无共同来源;
4. 日志缺号(中间/尾部)、前值对不上、提交号超出终止号 → 证据不足;
5. 签收行改挂单号、运单状态翻转带多签收行的边界场景;
6. CSV 缺列/重复键校验;
7. 续查包格式校验(携带 snapshots、终止号不大于起始号、缺 transactions);
8. 续查两批接力:区间/交集断言、跨批相邻区间合并(110–111、116–118);
9. 续查整批退回:缺号/前值不符后终点、批数、区间保持不变,改正后可从原终点重传;
   旧起点续包 → 终点已变;
10. 引擎克隆隔离:失败的续查不污染原状态;
11. 并发续查:两个线程从同一终点提交,恰一份生效、另一份终点已变;
12. 5 万条变更性能与正确性;
13. HTTP 接口:初查(含本轮链接)、轮次页/状态接口、续查两批、409 终点已变、
    整批退回后状态不变、未知轮次 404、样例下载。

## 已知限制

- 「已签收」状态值固定为 `已签收`(app/core.py 中 `SIGNED_STATUS`)。
- CSV 只校验必需列,额外列不参与比对。
- 证据包/续查包整体读入内存解析,未做流式 JSON;5 万条变更规模下足够。
- 行键(单号/签收号)在变更中不可改:after 行的键必须与记录键一致。
- 核查轮次只保存在同一服务进程内存中:进程重启、多副本部署或多 worker
  运行时,本轮链接不可用(需回到初查重新建立);如需跨进程共享,可把
  `RoundStore` 换成外部存储。
